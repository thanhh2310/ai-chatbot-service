📊 Đánh Giá Độ Chính Xác Mô Hình AI Chatbot Service

Phân tích chuyên sâu về kiến trúc RAG, LLM Routing, và Thuật toán Gợi ý cá nhân hóa

Cập nhật dựa trên kiến trúc Hybrid RAG & Cá nhân hóa mới nhất

1. Tổng quan Đánh giá (Overview)

Hệ thống hiện tại đã đạt đến mức độ phức tạp và tinh vi cao (Hybrid RAG, Personalization, Multi-turn Chat). Bạn đã áp dụng rất nhiều best practices trong việc truy xuất thông tin và gợi ý. Tuy nhiên, độ chính xác (Accuracy / Precision / Recall) của hệ thống sẽ bị ảnh hưởng bởi một số rủi ro tiềm ẩn ở các module tương tác với nhau.

Module Trạng thái hiện tại Điểm chú ý chính
LLM Router Khá Tốt Prompting chặt chẽ, Few-shot JSON output stability, Over-routing vào chat
Intent Extraction Rất Tốt Pydantic schema + Regex Fallback LLM hallucination khi user nhập lóng/sai chính tả
Vector Search Cần Chú Ý E5-large-instruct tốt nhưng embedding text chưa chuẩn hóa tối đa Mật độ thông tin trong vector, Semantic overlap
Reranking Cần Nâng Cấp Heuristic rule-based (keyword + user profile) Rules chồng chéo, dễ làm méo kết quả vector
Recommendation Rất Tốt Multi-signal weighted centroid Centroid drift (Nhiễu vector trung tâm khi sở thích quá đa dạng)

2. Phân tích chi tiết Điểm cần chú ý & Cách khắc phục

2.1. Vấn đề 1: Độ ổn định của LLM Router (agent_service.py)

Phân tích: LLM phân loại ý định qua việc sinh chuỗi JSON. Dù đã dùng temperature=0.0 và system prompt chặt chẽ, việc yêu cầu LLM tự sinh JSON (không dùng Native Tool Calling / Structured Outputs của Together AI / OpenAI) luôn tiềm ẩn rủi ro sinh ra format lỗi (thiếu ngoặc, parse lỗi), dẫn đến crash flow.

Ngoài ra, ranh giới giữa search_products và chat_with_bot đôi khi bị LLM hiểu sai nếu user hỏi nửa vời (ví dụ: "giày nike tầm 2 củ").

Cách sửa:

  • Native Tool Calling: Nên chuyển sang sử dụng tính năng tools và tool_choice hỗ trợ sẵn trong API của TogetherAI (Llama 3.3 hỗ trợ rất tốt tool calling) thay vì ép nó sinh JSON thuần trong text.
  • Ví dụ code sửa: 
    response = _client.chat.completions.create(
    model=_MODEL,
    messages=[...],
    tools=_TOOLS,
    tool_choice="auto" # Hoặc bắt buộc chọn 1 tool
)
# Lấy arguments từ response.choices[0].message.tool_calls[0].function.arguments
  • Fallback: Thêm khối try...except json.JSONDecodeError vững chắc hơn, nếu LLM route lỗi -> mặc định gọi chat_with_bot.

2.2. Vấn đề 2: Giai đoạn Reranking bị "Heuristic-heavy" (rag_service.py)

Phân tích: Hàm _rerank đang cộng dồn các điểm số một cách thủ công (hardcode weights):

  • final_score = 0.36 * vector_score + 0.20 * behavior + 0.14 * review + ... + boost_màu + boost_keyword

Hệ lụy: Việc cộng điểm thủ công này (Rule-based Reranking) rất khó tune (tinh chỉnh). Nếu một sản phẩm không liên quan nhưng vô tình khớp 1 keyword và có "behavior_score" cao (ví dụ: sản phẩm user hay mua), nó có thể bị đẩy lên trên một sản phẩm khớp chính xác ý định (vector_score cao) nhưng user chưa từng tương tác. Điều này làm mất tính chính xác của tìm kiếm.

Cách sửa:

  • Chuẩn hóa & Giới hạn Boost: Đảm bảo vector_score luôn đóng vai trò quyết định (chiếm ít nhất 60-70% trọng số). Các điểm personalization chỉ nên đóng vai trò tie-breaker (giải quyết khi 2 sản phẩm có vector_score tương đương).
  • Dùng Multi-stage (Pipeline) rõ ràng:
    1. Lọc Hard-filter (Category, Budget).
    2. Vector Search lấy Top 50.
    3. Dùng Cross-Encoder Model (như BAAI/bge-reranker-v2-m3) để tính điểm semantic (độ tương đồng ngữ nghĩa) thật chuẩn xác.
    4. Mới áp dụng nhẹ Personalization / Popularity Boost cho top 10.
  • Fix Regex Keyword Boost: Hiện tại re.search trong vòng lặp rất chậm và dễ sai sót. Việc boost keyword nên để Cross-Encoder lo, hoặc dùng BM25/Full-text search (Hybrid Search: Vector + Keyword) thay vì tự viết regex match.

2.3. Vấn đề 3: Nhiễu "Centroid Drift" trong Recommendation (recommendation_service.py)

Phân tích: Thuật toán _compute_weighted_centroid đang trung bình hóa các vector sở thích.
Rủi ro: Nếu user vừa thích mua "Giày bóng đá Nike" vừa thích mua "Áo thun Yoga hồng", vector trung bình (Centroid) sẽ nằm ở một điểm vô nghĩa giữa không gian vector (có thể trúng... "Quần bơi nam"). Trung bình hóa các sở thích khác biệt xa nhau làm mất đi tính cá nhân hóa chính xác.

Cách sửa:

  • Multi-Centroid (Phân cụm sở thích): Thay vì tạo 1 centroid duy nhất, hãy gom cụm (cluster) lịch sử tương tác của user thành 2-3 centroid (ví dụ: Cluster 1: Đồ đá bóng, Cluster 2: Đồ chạy bộ). Tìm top k sản phẩm cho mỗi centroid rồi trộn lại.
  • Cải tiến bằng Max-Sim: Thay vì tìm khoảng cách tới 1 Centroid, hãy tính khoảng cách của ứng viên tới từng seed product, và lấy score = MAX(similarity). Sản phẩm nào giống với bất kỳ sản phẩm nào user từng thích đều được điểm cao.

2.4. Vấn đề 4: Nội dung nhúng (Embedding Content) có thể bị "loãng" (sync_service.py)

Phân tích: Hàm _build_content nối tất cả thành một câu dài: "Danh mục: X. Thương hiệu: Y. Giá: Z. Mô tả: M. Phù hợp: G, S.".
Model multilingual-e5-large-instruct yêu cầu format đầu vào đặc thù (thường thêm prefix "query: " hoặc "passage: "). Nếu không đúng format, độ chính xác giảm đáng kể.

Cách sửa:

  • Chuẩn hóa E5 Prompt: Theo tài liệu của E5-instruct, text đưa vào database cần có prefix "passage: " và query tìm kiếm cần có prefix "query: ".
    Ví dụ lúc sync: content = f"passage: {built_text}"
    Ví dụ lúc query (rag_service.py): embed_query(f"query: {enhanced_query}")
  • Tối ưu text: Đưa các Keyword quan trọng (Tên SP, Thương hiệu) lên đầu. Giảm thiểu các từ nối không mang nhiều ý nghĩa (như "Các phiên bản màu sắc và kích cỡ là:").

2.5. Vấn đề 5: Lọc Phủ định (Negative Filtering) trong Intent Service

Phân tích: Hàm analyze_query yêu cầu LLM tách excluded_keywords (VD: "không lấy màu đen"). Giai đoạn Rerank lại dùng Regex để loại trừ cứng.
Vấn đề: "màu đen" có thể nằm trong mô tả theo kiểu: "Sản phẩm có 2 màu: Đen và Trắng". Nếu user tìm "áo trắng không lấy đen", Regex sẽ loại luôn sản phẩm này vì thấy chữ "đen" trong content, dù sản phẩm đó có màu trắng (đáp ứng đúng).

Cách sửa:

  • Thay vì dùng Regex loại thẳng trên chuỗi content (bao gồm cả mô tả dài), chỉ nên kiểm tra phủ định trên trường available_attributes (Màu sắc) hoặc trường tên sản phẩm.
  • Khuyến khích thiết kế Database có trường "Màu sắc" riêng biệt thay vì lưu gộp chung, để khi User nói "không màu đen", ta dùng câu lệnh SQL NOT ILIKE '%đen%' trên cột màu sắc đó, chính xác hơn Regex.

3. Tổng Kết Các Hành Động Khắc Phục (Action Items)

  • Khẩn cấp: Cập nhật format prefix "query: " và "passage: " cho mô hình E5 embedding để vector search hoạt động đúng công suất thiết kế.
  • Khẩn cấp: Đổi cách gọi LLM Router sang sử dụng Native Tool Calling API của TogetherAI.
  • Trung hạn: Giảm tỷ trọng của các điểm cộng tay (Heuristic boost) trong hàm _rerank, đảm bảo vector_score chiếm ưu thế tuyệt đối cho tính liên quan ngữ nghĩa.
  • Dài hạn: Thay đổi thuật toán Recommendation từ "Single Weighted Centroid" sang "Max-Sim" hoặc phân cụm để không bị trung bình hóa các sở thích trái ngược.
  • Dài hạn: Áp dụng Cross-Encoder Reranker để thay thế cho logic đếm keyword thủ công.
